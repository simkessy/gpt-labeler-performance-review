How should I read these charts?

For each run, we take the largest positive worker reading for the Java process. We then average those per-run peaks. This is not average use over time. The 95% view shows the value at or above 95% of usable readings. A result from six readings is not a safe production limit.

*The 5.6 GiB request is source-derived: 4 GiB for the main process plus about 1.6 GiB extra allowance. Seven input runs and one open-model publication run confirmed the 4 GiB heap. The extra allowance was not present in those saved configurations.

The workload filter uses a submitted cost-sample marker. It is not a verified parent-child join. The cost-calculation rows also use different workflows. The table pools unweighted available readings; it does not estimate population-wide memory use.

The larger warehouse study found roughly 49 GiB snapshots. The largest selected-history peak is not the month-wide maximum.

Why use these planning ranges?

The 3–5 hour assumption is informed by the multi-hour cost-estimation and pre-approval waits. We have not isolated how much of those waits is removable. The 30–45 minute assumption targets part of the 73-minute saved-label-to-publication interval while retaining output checks and final writing.

The combined 3½–5¾ hour scenario is a 28–46% reduction against the complete-timeline baseline. Benefits depend on eligibility, workload, and downstream queues. No controlled run has validated them.

Which claims remain unproven?

Actual time saved by the proposed changes. Pure model processing time. Actual driver memory peaks. Population-wide memory utilization. Money saved by idle-worker or empty-run removal. Whether memory specifically caused resource waits.

Configurations and worker task counts are measured or source-backed. The memory gaps justify controlled sizing tests. They do not establish unused memory percentages or a safe blanket reduction.
